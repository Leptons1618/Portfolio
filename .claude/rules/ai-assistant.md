# The AI assistant — what each module owns, and what its tests pin

Moved out of the root `CLAUDE.md` so it loads when you touch these files rather than in every
session. The trust-boundary rules that are *not* specific to this feature — `content-schema.ts`,
`authorize.ts`, `media.ts`, and the write endpoint — stay in `CLAUDE.md`.

## The two test commands

- **`npm run check:ai`** (`scripts/test-ai.mjs`) exercises the AI feature's security-relevant halves: that an API key cannot reach the admin listing (asserted against the **serialised** payload, because that is what leaves the Worker), that hidden projects and non-published posts never enter the assistant's corpus whatever the caller passes in, that the settings form cannot lift its own spending ceilings, that the input caps hold, that the scope filter refuses misuse *without* refusing real questions about the author, that every labelled-field key set round-trips and stays a pure function of the text so far when fed one character at a time, that a label belonging to one key set is not a field in another, that no context field a task declares can travel uncapped, that **no key which is not a sampling parameter survives `clampParams()`** — `max_tokens` above all, because that is the spending ceiling — that a vendor's model listing is read defensively enough that garbage produces an empty list rather than a throw, that a slash command is *looked up* in the task table rather than derived from what was typed, that **no lookup tool can reach a hidden project, a withdrawn post or a contact detail** whatever slug it is given, that the tool table is read-only by name and closed by schema, that a provider's output ceiling **raises** a task's and never lowers it and never passes the hard cap, that a `cache_control` breakpoint reaches only the two APIs that read one, that a run which produced nothing but deliberation is *reported* rather than rendered as an empty answer while a long think that then answers or looks something up is not, that the **daily schedule is off by default**, agrees with itself across the twenty-four ticks of a day, spreads across the window between days, stops after its configured attempts and cannot be handed an unbounded prompt, that a title a model wrote becomes a slug the write path accepts, and — the one that costs money if it regresses — that **the tool loop always terminates**, including against a stub model that asks forever. It deliberately does **not** assert that the scope *prompt* makes a model refuse an off-topic question — that is a property of a third party's weights, not of this code. It needs `scripts/ts-resolve.mjs`, a resolve hook that lets Node follow this repo's extensionless imports; that file explains why the alternatives are worse.
- **`npm run probe:ai`** (`scripts/probe-ai.mjs`) is the other half of `check:ai` and is deliberately **not** in `npm run check`: it calls a real provider with the `OPENROUTER_API_KEY` from `.env`, so it needs a credential CI does not have and costs a fraction of a cent. It exercises what a network-free test cannot — that `GET /models` still parses through `normaliseModels()`, that the request body this repo builds is one a vendor accepts, and that a streamed answer with tools drives the frame protocol, the tool loop and `thinkStripper()` end to end. It prints the **thinking-vs-answer split**, which is the number the AI screen's limits are actually about: a run that spends its ceiling deliberating and truncates looks, from every other angle, like a working call. Run it after changing anything in `ai.ts`, `ai-catalog.ts` or `ai-tools.ts`. `--model <id>` overrides the default, and expect to need it — model ids get retired.

## `src/lib/` — the AI half

The AI assistant is a handful more, and the split between the first four is deliberate — they are four different failure modes and only three of them are testable without a network:

- **`ai.ts`** — *who answers, and what it may spend.* Provider rows, settings and their clamps, the OpenAI-compatible call with fallback across active providers, the SSE→NDJSON re-encoder, and **`agentStream()`**, the bounded loop that runs a model's lookups. `effectiveMaxTokens()` is the ceiling rule, and it is **additive**: the answer keeps the whole of `requested`, and thinking gets up to `THINKING_HEADROOM` *more* on top — never more than the answer's own budget, capped by the provider row where it names a maximum, never past `MAX_OUTPUT_CEILING`, and never reduced below `requested`. The old shape, `max(requested, min(row, HEADROOM))`, collapsed to `requested` for any task asking for the headroom or more, so `/write-whole-post` at 4,000 had 4,000 for the deliberation *and* the post — the bigger the task, the less room it had. Decisions 37, 43 and **51**. `thinkingBudget()` is the other half of the same pair (ceiling minus answer), and it exists to quantify the report below, not to gate anything. `AiSettings.reasoningEffort` is the other half of the same problem and the only one that moves the thinking/answer *split*; it ships `low` and **both** endpoints pass it explicitly now. `/api/ai/assist` resolves four levels, most specific first — the panel's picker, the AI screen's setting, the provider row, then `low` — and always sends the field. Sending nothing is not "no thinking", it is the vendor's default, and the vendors that default to anything default to more; that was half of decision 51's failure. `wireMessages()` turns a message's `cache` flag into an `cache_control` breakpoint for the two APIs that read one and drops it everywhere else. A provider is three strings because OpenRouter, OpenAI, Groq, Together, DeepSeek and a local llama.cpp all speak the same `POST {base_url}/chat/completions`; there is deliberately no adapter interface. **`summarise()` builds the admin's view key by key and never by spreading a row** — that is the line stopping the API key reaching a response, and `check:ai` pins it. It is also where **reasoning is separated**: `thinkStripper()` splits `<think>`-family blocks out of `content`, sniffs the *opening* of a response for unmarked narration ("Here's a thinking process:") that no tag marks, and routes all of it — along with `delta.reasoning` and `delta.reasoning_content` — into `{"thinking":…}` frames. Nothing is sent to *suppress* reasoning any more: the `reasoning: { exclude: true }` this used to carry for OpenRouter never stopped the leak (the models that hurt narrate in `content`) and threw away the deliberation every surface now shows. The answer travels as `{"delta":…}` and nothing else; the two never mix, which is what lets every surface show thinking in a closed `<details>` and write only the answer into a field. Decision 29.

  `sseEvents()` also **reports a round that was nothing but thinking**: no answer text, no tool call, some deliberation, and an `error` frame goes out naming what it spent and the three settings that change it. Before that, such a run was a completed answer of zero characters, which reads on every surface exactly like a dead key or a retired model id. It fires at the *end* of the round and deliberately not mid-stream on a budget — a round that thinks hard and then asks to read a post is the tool loop working, and a watchdog could not tell that apart from a runaway while the tokens were still arriving. `check:ai` pins both halves: that the report fires, and that a long think followed by a lookup or by an answer is never reported. Decision 51. **`callChat` walks models and then providers**, so a 429 or a retired model id falls through to the next entry in `fallback_models` on the same key — decision 32.
- **`ai-corpus.ts`** — *what it may know.* Builds the grounding markdown from published content, and **re-applies the public-visibility filters on what it was handed rather than trusting its caller**. That redundancy is the design: `content.ts` filtering is a convention, `buildCorpus()` filtering is a function with a test. It is also stricter than `getPosts()` — that shows drafts in `dev`, and a machine answering strangers must not. Email, phone and address are never included. **`buildIndex()` is what a request actually carries now** — a line per thing with the slug a tool takes — and `buildCorpus()` survives because the admin screen reports both sizes and the difference between them is the saving. Both apply the same filters and both are tested against a hidden project and a withdrawn post.
- **`ai-tools.ts`** — *how it gets it.* Five read-only lookups (`search_content`, `read_post`, `read_project`, `read_case_study`, `read_resume`), each a JSON Schema and a handler, each going back through `publicProjects()`/`publicPosts()` rather than trusting that the caller filtered. **Nothing here writes, and nothing takes anything that becomes SQL** — that is the line that keeps decision 24's argument intact while a model chooses what to read; decision 37 states it precisely. `check:ai` asserts the naming rule (`search_`/`read_`/`list_` only), the closed schemas, and that a withdrawn post is unreachable through every one of them.
- **`ai-guard.ts`** — *what it may be asked.* The scope prompt, `screenQuestion()`, the input caps, and the rate limiter. Read its header before changing anything: it is explicit that the prompt and the pattern filter are both **weaker** than the budget, which is the one that holds. `screenQuestion()` refuses the unmistakable misuse shapes before a provider is called; it is written for precision, not coverage, and the seventeen legitimate questions in `check:ai` are what keep it that way. Decisions 23 and 27.
- **`ai-catalog.ts`** — *what a provider is, before anyone has answered anything.* The vendor presets the AI screen's dropdown is built from, `normaliseModels()` for whatever a vendor's `GET /models` returns, and `PARAM_SPECS` + **`clampParams()`**, which is a trust boundary in the same sense `content-schema.ts` is: what it returns is spread into an outbound request body, so its keys come from source and never from a row. Imports nothing, so `check:ai` can call it directly. Decisions 33 and 34.
- **`assist-panel.ts`** — *the conversation.* The shared authoring panel: the message log, the slash-command composer, the per-message thinking disclosure, the lookup rows, the run toolbar (model / effort / lookups), the resize grip, and the session history. Mounted by both authoring screens against `AssistPanel.astro`. It owns conversation; the page owns its own fields and is handed a `Turn` to write into. Decisions 35 and 37.
- **`assist-tasks.ts`** — the fourteen things the authoring assistant can be asked to do, each with its own temperature, token ceiling and **allowlist of which editor fields are sent**. A closed table, not a forwarded prompt — decisions 24 and 31. Ten belong to the journal editor and three to the project screen; **`task.surface` is what decides, and each screen offers `ASSIST_MENU` filtered to its own name**, so a task appears in exactly one place and no page script changes to receive it. Each task also carries a **`command`** — `/write-whole-post`, `/draw-diagram` — written out rather than derived from the label, because a label is copy and a command is an interface. `chat` is the exception: `surface: 'both'`, no command, no `live` target, and the only task that is given the conversation so far. Decision 35. It is also the only task with *two* output shapes — a question gets prose, and a request to change a field gets the change, as labelled fields the editor applies. **`parseEdit(text, shape)`** is what tells them apart, and it is stricter than `parseFields` on purpose: an edit has to *open* with a label, or a paragraph mentioning one would be written into the post. Decision 48. `task.live` names the field a task streams into, or is absent for the panel-and-Insert path. `task.context` is typed `AssistField`, a closed union, because a field missing from `CONTEXT_LIMITS` slices to `undefined` — which is not a cap, it is the whole value — so a typo there would be an *uncapped* field on a metered call. **`parseFields(text, shape)`** at the bottom reads a labelled-field response against the shape the task names (`POST_KEYS`, `PROJECT_KEYS`, `CASE_STUDY_KEYS`) and is called on every delta, so it must stay a pure function of the text so far — decision 28; `parseDocument()` survives as the post-shaped wrapper. It reports `recognised: false` for a response carrying no label at all rather than falling back to treating the lot as body text; that fallback is how a reasoning model's deliberation ended up inside a post — decision 29. Each task also declares a `group`, which is the only thing deciding which of the panel's three shelves it appears on.
- **`diagram.ts`** — Mermaid source → SVG → the `media` table. Mermaid is dynamically imported here so it is a chunk fetched on first use, never part of the admin bundle and never on a public page. Takes the GitHub token as a *parameter* rather than importing `github.ts`, which is what keeps it loadable outside a bundler for `check:ai`. Decision 25.
- **`journal-auto.ts`** — *the schedule.* When the daily post is due, what it is asked for, and what the last run did. **It imports nothing**, and that is load-bearing twice: it is reached from `ai-store.ts`, which is browser code, so a value import of anything server-side would drag Astro's markdown processor into the admin bundle; and being import-free is what lets `check:ai` drive a year of days through `decide()` directly. `hourFor()` hashes the date rather than rolling a number, so all twenty-four ticks of a day agree with no stored state; `decide()` is the whole schedule as a pure function of a clock and two `documents` rows. The two functions that need a database live in `/api/ai/daily` beside their only caller. **Every hour it stores is UTC and must stay UTC** — the tick is a GitHub cron, `hourFor()` hashes a UTC date, `decide()` compares against `getUTCHours()`, and a local-time field would be a stored number that shifts twice a year. `/admin/ai` renders the same window in the browser's own zone underneath the fields, live as they are typed, and never writes a converted value back. Decision 52.
- **`ai-store.ts`** — the browser half. Writes go through `POST /api/content` like everything else; the one rule it adds is that **an untouched key field must not clear the stored key**, so `saveProvider` omits a blank `apiKey` and `clearKey()` is a separate, deliberate call.

## The endpoints

Four of the five are the assistant answering something. The fifth is a clock.

- **`/api/ai/chat`** — the public one, and the only unauthenticated thing on this site that spends money. Checks run cheapest-first and the limiter charges before the call.
- **`/api/ai/assist`** — the authoring one. Takes a *task name*, never a prompt, and always sends an effort (see `ai.ts` above).
- **`/api/ai/chats`**, **`/api/ai/providers`**, **`/api/ai/models`**, **`/api/ai/status`** — storage and configuration.
- **`/api/ai/daily`** — the schedule. `POST` runs a tick, `GET` reports what the next one would do without consuming an attempt. Read its header before changing it; four things there are deliberate:
  - **Two callers, two powers.** `CRON_SECRET` (a Worker secret, compared in constant time, and *shut* when unset) buys asking whether it is time. The owner's GitHub token — the AI screen's "Run now" — is the only thing that may `force`. A leaked schedule secret cannot spend the day's budget in a loop.
  - **The attempt is recorded before the generation**, not after. Same reasoning as the rate limiter charging before the call: an attempt recorded on the way out is not recorded at all when the isolate dies mid-generation, which is the expensive case.
  - **It writes a `draft`,** through an `INSERT` whose every column name is a literal in that file. It is a second write path because `/api/content` authenticates a *person* and there is no person here — the rule that endpoint enforces is kept rather than borrowed, and nothing in a request to this route reaches the statement at all.
  - **The answer is drained through `agentStream`,** not read from a non-streaming completion. A non-streamed `content` carries a reasoning model's deliberation with nothing between it and `parseFields`; decision 29 is a property of the frame protocol, and this is what makes that true off the browser.

  The prompt is the existing `compose` task with a generated topic steer — deliberately *not* a new entry in `ASSIST_TASKS`, which is the table of things the panel offers. Decision 52.
