How AI powers the admin

One route, one closed task table, one engine shared with the public chat and nothing else in common with it. This page walks every AI feature in the admin: what it does, which files make it true, what it is allowed to write, and where every limit lives.

The mental model

src/pages/api/ai/assist.ts · src/lib/assist-tasks.ts · src/lib/assist-panel.ts · src/lib/ai-store.ts

Three ideas explain the whole feature:

  1. The assistant drafts; it never saves. Every AI output lands in the editor as text. Publishing still happens through the same Save button a person presses. An agent that could write a row would be an agent that could publish.
  2. The task list is closed. /api/ai/assist looks the task name up in a source-level table. A name that isn't there gets a 400 listing the valid names — never a forwarded prompt. That keeps the honest claim "there are sixteen things this endpoint can be asked to do" instead of the weaker "only the owner can call it".
  3. It is independent of the public switch. settings.enabled governs whether strangers may ask questions. Turning the public assistant off must not take away the author's own tools; the assist route only checks that a keyed provider exists.

The task table

src/lib/assist-tasks.ts — ASSIST_TASKS, the single source of truth

Nineteen tasks. Each declares its prompt contract, output format, ceilings, sampling temperature, required context fields, and how its output reaches the editor. The route refuses anything not in this table; the editors render their buttons from ASSIST_MENU, so UI and server cannot drift apart about what exists.

Two design rules worth knowing when extending the table: tasks whose output replaces text the author already wrote are deliberately not live — they preview first, because "it is written, press Undo" is the wrong offer for a range the author chose. And every anti-fabrication rule in the prompts ("invent no benchmark", "slugs must come from the index") exists because the failure mode of a writing model on a portfolio is plausible invention, not refusal.

Voice grounding

needsCorpus: true → buildIndex() over published content only

Drafting tasks set needsCorpus. The route then fetches all four content tables and builds buildIndex() — the same filtered table-of-contents the public chat uses, so new prose matches the author's existing voice and reuses their real tags and slugs. Reformatting tasks (tighten, diagram, resume bullets) skip the four queries and several thousand tokens entirely.

The request path, end to end

src/pages/api/ai/assist.ts

  1. requireOwner(request) before the body is read at all. The browser sends the GitHub user token sign-in issued; the Worker asks GitHub who it belongs to and requires login === site.githubUser. No site-owned API key exists; revocation belongs to GitHub (sign-out, ~8-hour expiry, App uninstall); it fails closed even when GitHub is unreachable.
  2. Closed lookup: isAssistTask(task) or 400 with the valid names — the honest claim is "there are nineteen things this endpoint can do", not "only the owner can call it".
  3. Provider check: at least one active row holding a key, else 503 with copy naming the fix.
  4. Model pinning: the panel may pass a model id, but pickModel() accepts only ids present in configured provider rows — a stolen session cannot name an arbitrary expensive model.
  5. Prompt assembly: assistPrompt() builds the system message from the task's instructions, the owner's persona string, the requested context fields (each individually capped), trimmed conversation turns (roles other than user/assistant are dropped, so nothing in a stored transcript can become a second system message), and the tool summary when tools are offered.
  6. Stream: NDJSON out — {"thinking":…} frames separated by the engine's stripper, then {"delta":…}, plus {"tool":…} provenance rows for lookups. Vendor error text is shown in full here (the reader is the owner; it names the wrong model or empty account), unlike the public route where it stays server-side.

The tool loop behind drafting

src/lib/ai.ts — agentStream()

Tasks given the index may also be given the five read-only lookup tools (search_content, read_post, read_project, read_case_study, read_resume). The loop bounds itself three ways: round count (3 default), total calls (MAX_TOOL_CALLS = 8), and — the part that makes those real — the tools are withdrawn once spent rather than merely forbidden, because a limit a model is told about is a limit it asks past. Later rounds pin to the provider that answered round one; half an answer from each of two vendors is two conversations spliced, not fallback.

The AI settings screen

src/pages/admin/ai.astro · src/lib/ai-store.ts · GET+POST /api/ai/providers · GET /api/ai/models

  • Providers are rows in ai_providers: label, base URL, model, optional assist-only model, active flag, priority order. Any OpenAI-compatible vendor works without an adapter. Multiple active rows are a fallback chain — failures walk down the priority list instead of erroring at a visitor.
  • The key is write-only from the screen's point of view. The form sends it only when newly typed; an empty field means "leave it alone". Reads return a masked fingerprint via summarise(), built key-by-key so a future column cannot ride along. scripts/test-ai.mjs asserts the serialized response cannot contain the key.
  • Test button = a real completion. POST /api/ai/providers sends an 8-token request to exactly the chosen row — not through the fallback walk, so a broken primary can't borrow a healthy backup's green tick. Model listing succeeds on some vendors with keys that cannot run inference, which is why listing is not the test.
  • Model picker backed by a proxy. GET /api/ai/models asks {baseUrl}/models (key outbound only, 15s timeout) and rebuilds the vendor's JSON into the seven fields the site uses. Failures come back as { models: [], error } at 200 — ordinary states of a form mid-typing, not exceptions.
  • Settings are clamped twice. The screen saves through clampSettings(), whose ceilings (≤60/hour per IP, ≤2000/day, ≤ MAX_OUTPUT_CEILING tokens) exist because the one person who can reach the form is the one person whose typo spends their own balance. Decision 22: a settings screen may not lift its own limits.
  • Cost visibility. The screen reports corpus vs index sizes side by side (the difference is the retrieval saving) and today's usage — answers served and distinct callers — from the same counter table the budgets charge.
  • Public switch semantics. The toggle writes the raw stored value, not the folded readiness /api/ai/status reports — otherwise a switch reading back off because no key was pasted yet would be a control refusing to stay where it was put.

Transcripts: ai_chats / ai_messages

migrations/0007_ai_chats.sql · /api/ai/chats · migrations/0008_ai_agent.sql

  • Conversation ids are generated by the browser, so streaming can start before any server round-trip names the thing.
  • A chat is pinned to a surface (journal / project) because commands and fields differ; history listed in the wrong editor would be unresumable there.
  • doc_slug is nullable and deliberately not a foreign key: a draft that was abandoned keeps its conversation readable, and journal/new has no slug yet.
  • Messages have a third role, note — the panel's own voice ("stopped", "nothing was written"). Stored so transcripts don't silently lose events; kept a separate role so it can never be replayed to a model as an assistant turn.
  • thinking is stored beside the answer, never inside it — the storage shape mirrors the wire protocol's separation.
  • Caps bound runaway loops, not people: 20 000 chars/message, 400 messages/chat, 60 chats listed. The route uses fixed hand-written SQL (no identifier interpolation) because append needs autoincrement ids the generic slug-keyed endpoint cannot express.

The asymmetry is deliberate: the admin surface authenticates every call and therefore needs no rate limiter; the public surface authenticates nobody and therefore meters everything.

Failure behaviour

  • Vendor down: the walk moves to the next active provider; only total failure surfaces, as the vendor's own words in the panel.
  • Stream dies mid-answer: partial deltas already delivered stay in the editor; the panel appends a note frame explaining the stop; the transcript records the note.
  • Stop button: aborts the fetch; the snapshot taken before the run restores the pre-stream state via the same Undo path.
  • No provider configured: 503 with copy pointing at the AI screen — the editors grey their assist controls rather than sending requests that cannot succeed.
