# Taste
- User files requests as brief, informal, bug-report-style notes referencing UI elements by their visible names ("Choose a model modal", "import project modal"), often bundling two asks in one message; expects targeted fixes without lengthy back-and-forth. Confidence: 0.7
- Changes to UI must match established sibling patterns — reuse existing components/conventions rather than inventing parallel treatments (explicitly asked for the model-picker modal to behave "just like import project modal"). Confidence: 0.85
- Async operations (OAuth sign-in, redirects, network round-trips) must show immediate feedback from the first frame — busy indicators, staged status text ("Redirecting… → Signing you in… → Signed in. Redirecting…"), disabled buttons while in flight — because a silent wait window reads to the user as "it didn't work". Confidence: 0.85
- Values interaction feel and motion polish: requested a loading/sign-in animation so the flow "feels smooth"; subtle entrance animations and a consistent motion grammar are welcome, not scope creep. Confidence: 0.8
- Mirrored/symmetric UI states must behave identically — flagged the docked-right placement showing two icons while docked-left was correct and asked for the right side to be updated "similarly"; asymmetric handling of equivalent states reads as a bug. Confidence: 0.7
- Floating panels must not cover the content they assist; prefers space-reserving layouts where the page shrinks/makes room next to the docked panel ("so that it doesn't block the page view") over pure overlays. Confidence: 0.7
- Features should act on natural-language input directly: a plain request like "update the case study" should auto-select the matching command/skill and apply the change to the data, not fall back to replying in chat; requiring exact /command syntax was treated as a defect. Confidence: 0.8
- Nothing that lands in version control may credit the agent or tooling: explicitly asked to amend a commit to drop a `Co-Authored-By: Claude` trailer, and the same applies to PR titles/bodies and generated-with lines. Confidence: 0.85
- A reported defect is expected to land as a focused fix plus a regression test covering it, and to be cleared before moving on to the next piece of work (handed back two `job-view.ts` bugs with "plus a test each" and asked to fix them before continuing the phase). Work is test-first: "write the failing test first, watch it fail, then fix, then watch it pass", and fixing only what is listed — no drive-by refactoring or new features. Confidence: 0.8
- Control flow must be driven by data, not by matching display copy: flagged a button whose action was chosen by matching its label text ("Paste the advert", "Open the notes") and required the model/selector to return the action itself so rewording a label cannot silently break behaviour. Confidence: 0.75
- Scripted browser tests are not accepted as proof of keyboard/focus behaviour; expects the real-keyboard path to be exercised by hand ("my scripted test left focus on a field inside the closed dialog… should check it by hand"). Confidence: 0.6
- Privacy-first about data: the owner's own text must be rendered as text (createElement/textContent, never innerHTML or HTML templates), application record data must never travel in a URL, and fixtures/screenshots must use invented names (Acme, Priya Nair, Arjun Mehta) rather than real people or companies. Confidence: 0.8
- Keeps the dependency and design-system surface closed: no new dependencies, and visual styles must reuse the existing spacing tokens (`--space-1/2/3/4/6/8`) and existing components/helpers instead of ad-hoc values or duplicate implementations. Confidence: 0.75
- Documentation must describe the current state of the code, never the history that produced it: "state what is true of the code as it now is; do not describe the phases", while first reading each file's existing entries and matching their voice and depth. Confidence: 0.8
- Preconditions on an action must be visible before the click, not only reported after it: asked for the leaving-a-dirty-page button to be disabled with the blocking reason as its title and kept in sync with the dirty state, rather than only toasting an error once pressed. Confidence: 0.65
- Uses `uv` to manage Python interpreters/environments and expects Python-related setup or errors to be resolved through uv rather than system `python`/`py` installs or store-provided interpreters ("i've uv installed and uv manages python"). Confidence: 0.8
- Wants completion reports in four fixed parts — Discovered / Changed / Verified / Not verified — with the verification section stating plainly which checks were done by hand and which were not, rather than leaving gaps unmentioned. Confidence: 0.7
